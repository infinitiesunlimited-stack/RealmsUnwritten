# AI Development Rules

## Purpose

These rules govern Claude, Codex, and other coding or design agents working in this repository. They apply to analysis, specifications, data changes, implementation, tests, refactors, and documentation.

An agent's task is to execute the approved scope faithfully, preserve architectural consistency, and leave verifiable evidence. It is not to redesign the game opportunistically.

## Authority and required reading

Before changing project files, an agent must read:

1. The user's current request and any task-specific specification.
2. `DESIGN_CONSTITUTION.md`.
3. Relevant sections of `HIGH_LEVEL_ARCHITECTURE.md` and `DATA_MODEL_OVERVIEW.md`.
4. The applicable milestone scope in `PROTOTYPE_0_1_SCOPE.md` or later approved specification.
5. Repository-local agent instructions and ADRs that govern the touched area.

If instructions conflict, stop the conflicting work, identify the exact conflict, and request Creative Director or architectural review. Do not resolve a constitutional conflict by quietly following existing code.

## Scope discipline

- Do not write production game code unless the task explicitly authorizes implementation.
- Change only what is necessary for the approved task.
- Do not redesign, reformat, rename, or "clean up" unrelated systems.
- Do not add speculative future systems because architecture documents mention them.
- Do not turn a prototype simplification into a permanent abstraction without review.
- Preserve user work and unrelated local changes.
- Prefer a small complete vertical change over broad partial scaffolding.
- If a dependency is missing, report it; do not fabricate a parallel substitute that creates a second source of truth.

## Constitutional compliance

All changes must respect `DESIGN_CONSTITUTION.md`, especially:

- People are not generated by buildings.
- Households connect people to residence and ordinary domestic economy.
- Physical goods have quantity, custody, location, and auditable transfers.
- Land-based production uses physical land.
- Knowledge has carriers and is not an instant date/research-point unlock.
- AI, UI, and Unreal Actors do not own authoritative simulation truth.
- Scaling must not require every distant person to run expensive per-frame behavior.
- Historical starting conditions do not imply scripted outcomes.

An agent must call out any requested implementation that appears to violate these constraints before implementing it.

## Interface and ownership rules

- Do not silently alter public interfaces, serialized structures, data asset formats, command schemas, domain events, units, or semantic meaning.
- State the owner of new authoritative data.
- Use the established command/query/event boundaries; do not reach across systems to mutate foreign state.
- Do not introduce duplicate authoritative fields for convenience.
- Mark cached or derived values and provide an invalidation/rebuild strategy.
- Use stable simulation IDs across persistence and presentation boundaries; do not persist raw Actor/UObject references as world identity.
- Distinguish definition IDs from runtime entity IDs.
- Distinguish ownership, custody, location, residence, access, and jurisdiction.
- Preserve transactional invariants when a change touches multiple entities.

If an interface must change, the agent must present:

1. The current contract.
2. The proposed contract and reason.
3. Every known caller, data asset, test, save schema, and document affected.
4. Compatibility or migration strategy.
5. Approval status.

No call-site compilation fix is a substitute for semantic review.

## Unreal Engine boundaries

- Do not place authoritative simulation state only in Actors, components, widgets, animation instances, level scripts, or visual Blueprints.
- Do not use Actor Tick for routine domain updates by default.
- Presentation objects may cache read-only views and interpolate visual state.
- Animation notifies and effects may request or display outcomes; they do not create authoritative goods, complete production, age people, or advance crops.
- Unloading, pooling, or destroying a representation must not destroy its persistent simulation entity.
- Core high-volume rules must be runnable in headless tests without rendering.
- Use Blueprints for bounded presentation/content assembly where appropriate; do not bypass domain validation for convenience.
- New engine dependencies, plugins, or major framework commitments require approval and documented alternatives.

## Performance rules

Every implementation proposal must identify its expected population/entity scale and update cadence.

Agents must:

- Avoid per-frame work per person, household, good lot, field, or distant entity.
- Prefer scheduled wake-ups, relevant events, batched passes, threshold invalidation, and analytical elapsed-time updates.
- Bound pathfinding, planning, allocation, and query work.
- Use spatial and domain indexes for repeated searches.
- Prevent unconstrained all-people-by-all-jobs or all-inventories-by-all-resources scans.
- Treat allocations, UObject/Actor counts, event volume, save size, and memory as performance risks, not only frame time.
- Add or update a representative benchmark when a high-volume path changes.
- Report measured results and test conditions; do not claim scalability from intuition.

Optimization must preserve conservation, identity, and causality. Aggregation needs documented merge, de-aggregation, and loss-of-detail rules.

## Historical and content rules

- Do not convert a local or late-period historical practice into a universal rule without evidence.
- Record geographic scope, date range, source, confidence, and gameplay interpretation for research-driven data.
- Separate sourced facts from plausible inference and deliberate gameplay abstraction.
- Avoid deterministic cultural traits or permanent faction bonuses standing in for institutions and circumstances.
- Treat names, identities, religions, cultures, and conflicts with specificity and care.
- Do not use generated-looking citations; verify research sources before recording them.

## Testing requirements

Every behavior change requires proportionate automated tests. At minimum:

- Domain rules receive focused unit tests.
- Cross-system material chains receive scenario/integration tests.
- Every bug fix receives a regression test when technically feasible.
- Transfers and production test conservation and duplicate-prevention.
- Relationship changes test both ends and orphan prevention.
- Random outcomes use controlled seeds in tests.
- High-volume paths receive performance or benchmark coverage.
- Save-schema changes receive round-trip and migration tests under the declared compatibility policy.

Tests must verify outcomes and invariants, not merely that a function was called. Do not weaken, delete, skip, or rewrite a failing test solely to make a change pass. If an approved behavior change invalidates a test, explain the semantic change in the same work item.

Before completion, run the narrowest relevant tests and then the applicable broader suite. Report the exact commands, results, and any tests not run.

## Save compatibility and data migration

- Every serialized format must have an explicit version once introduced.
- Determine the milestone's compatibility policy before changing serialized state.
- When compatibility is required, provide a migration, validation, representative old-save fixtures, and rollback/error behavior.
- Preserve stable entity IDs and relationships through migration.
- Account explicitly for removed or transformed people, goods, reservations, property rights, jobs, and scheduled events.
- Never silently discard unknown or invalid authoritative data to make a save load.
- If compatibility is intentionally broken during an approved prototype window, document the break and increment the schema/version marker.

## Documentation and change records

Update documentation in the same change when behavior, interfaces, data ownership, schema, units, or workflows change.

A completed implementation report must include:

- Summary of changed behavior.
- Files and systems touched.
- Interfaces/schema affected and compatibility status.
- Tests and benchmarks run with results.
- Performance risks and measurements.
- Known limitations, prototype shortcuts, and follow-up work.
- Documentation/ADR updates.

Use an ADR for decisions that alter system boundaries, persistence, core data layout, scheduling, determinism, third-party dependencies, or a durable project convention. Do not rewrite old ADRs to hide superseded decisions; add a superseding record.

## Architectural review triggers

Request review before implementing any change that:

- Moves authoritative data between systems or layers.
- Adds a second source of truth.
- Introduces a global service with broad mutation access.
- Changes stable ID/reference behavior.
- Breaks or reinterprets a public interface or domain event.
- Changes serialized schemas or compatibility guarantees.
- Selects/replaces ECS, Mass, UObject, database, navigation, networking, or persistence foundations.
- Changes simulation step, ordering, scheduling, determinism, or random-stream policy.
- Introduces aggregation or simulation LOD that can affect outcomes.
- Adds a new plugin, engine module, online service, or license obligation.
- Makes a major structural refactor or moves ownership across module boundaries.
- Conflicts with or requires amending the constitution.

Until review is granted, agents may inspect, measure, research, write an options analysis, or create an isolated disposable spike if explicitly authorized. They may not merge the structural change into production architecture.

## Required work sequence

For an implementation task, agents should follow this order:

1. Restate the accepted outcome and list governing documents.
2. Inspect the relevant implementation, tests, data, and current local changes.
3. Identify authoritative owner, boundaries, invariants, and save implications.
4. Propose the smallest compliant change; raise review triggers before coding.
5. Write or update tests that express the intended behavior.
6. Implement without unrelated redesign.
7. Run tests, validation, and proportionate performance checks.
8. Inspect the final diff for scope creep, accidental interface changes, generated files, and missing documentation.
9. Report evidence and unresolved risks clearly.

Do not claim completion when required tests were not run or when a known blocker prevents the requested outcome.

## Prohibited shortcuts

Agents must not:

- Create a global resource counter as the authoritative inventory.
- Spawn people from housing capacity.
- Let UI or AI write domain records directly.
- Use visible Actor existence as simulation existence.
- Hide transfer by teleporting goods between inventories without an approved abstraction and travel state.
- Unlock technology because a year threshold was crossed.
- Resolve performance by deleting identity or material quantities without approved aggregation rules.
- Catch and ignore invariant, migration, or data-validation failures.
- Add silent fallback behavior that fabricates missing authoritative data.
- Change units or rounding rules without migration and tests.
- Commit credentials, private keys, machine-specific paths, build output, or derived caches.
- Present unmeasured performance claims or unverified historical assertions as facts.

## Handling ambiguity

Agents should make small reversible assumptions only when they do not alter architecture, product behavior, historical interpretation, compatibility, or scope. State such assumptions in the work report.

Ask for direction before choosing among options that materially affect player experience, authoritative ownership, save data, public contracts, historical framing, dependencies, or long-term performance strategy.

When encountering an unrelated defect, record it separately. Fix it only if it blocks the authorized task and the smallest safe correction is clear; otherwise do not broaden scope.

## Definition of done for agent work

Work is done only when:

- The requested outcome is present and within scope.
- Applicable constitutional and architectural rules are satisfied.
- Interfaces and authoritative ownership are explicit.
- Tests pass at the required levels.
- Save and migration status is known.
- Performance risk has been assessed with evidence appropriate to the change.
- Documentation and ADRs are current.
- No unrelated changes or machine-generated debris are included.
- Limitations and unrun checks are disclosed.

## Recommended repository and document structure

The following structure keeps governing design, research, specifications, source, tests, and generated Unreal content distinct. Directories should be created only when their phase begins; this is a target layout, not a request to scaffold implementation now.

```text
/
|-- README.md                         # Project entry point and document map
|-- GAME_VISION.md                    # Product north star
|-- DESIGN_CONSTITUTION.md            # Non-negotiable laws
|-- HIGH_LEVEL_ARCHITECTURE.md        # Durable boundaries and system map
|-- PROTOTYPE_0_1_SCOPE.md            # First vertical-slice contract
|-- DEVELOPMENT_ROADMAP.md            # Capability gates and sequencing
|-- DATA_MODEL_OVERVIEW.md             # Conceptual entities and invariants
|-- AI_DEVELOPMENT_RULES.md           # Rules for coding/design agents
|-- AGENTS.md                          # Repository-local operational instructions
|
|-- Docs/
|   |-- ADR/                           # Numbered architecture decision records
|   |   |-- 0000-template.md
|   |-- Design/                        # Approved feature specifications
|   |   |-- Systems/
|   |   `-- UX/
|   |-- Research/                      # Evidence, citations, confidence, implications
|   |   |-- Regions/
|   |   |-- Economy/
|   |   |-- Agriculture/
|   |   |-- Society/
|   |   `-- Warfare/
|   |-- Prototypes/                    # Results, metrics, shortcuts, exit reviews
|   |-- DataSchemas/                   # Human-readable schema/contracts and versions
|   |-- Testing/                       # Test strategy and benchmark definitions
|   `-- Glossary.md                    # Canonical domain terminology and units
|
|-- Config/                            # Unreal and project configuration
|-- Content/                           # Unreal assets and data assets
|   |-- Core/                          # Shared, non-regional content
|   |-- Regions/                       # Historically scoped regional content
|   |-- Prototypes/                    # Clearly labeled temporary content
|   `-- UI/
|-- Source/                            # Production modules when authorized
|   |-- SimulationCore/                # Headless authoritative rules and records
|   |-- SimulationSystems/             # Domain modules with explicit ownership
|   |-- Application/                   # Commands, orchestration, read models
|   |-- DecisionAI/                    # Planners and policies; no world ownership
|   |-- Presentation/                  # Unreal representations and adapters
|   `-- GameUI/                        # UI consuming read models/commands
|-- Tests/
|   |-- Unit/
|   |-- Scenario/
|   |-- Persistence/
|   |-- Performance/
|   |-- Fixtures/
|   `-- HistoricalData/
|-- Tools/                             # Validation, import, profiling, save migration
|-- Plugins/                           # Approved project plugins only
`-- Build/                             # Build scripts/config; generated output ignored
```

Root source-of-truth documents stay easy to discover. Detailed specifications link upward to the constitution and architecture; ADRs explain durable choices; research records support historically scoped data; code modules mirror the four-way separation between authoritative simulation, application boundaries, AI decisions, and representation.
